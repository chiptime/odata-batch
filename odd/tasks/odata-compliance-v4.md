# odata-compliance-v4

Objective: close the remaining OData v2 compliance gaps and add OData v4 (multipart and JSON batch) support.
Branch: `fix/redirect-credential-leak` (no commits until the user authorizes them; see L2). Delivery: ask-on-risk; T3 is BREAKING, so the next release is 4.0.0 (user decides). Test runner: `npx jest` (+ `npm run lint`, `npm run format:check`, `npx tsc --noEmit -p tsconfig.json`).

## Specs

- **S1 Timeout / size limits.** User choice: "Timeout configurable" — "Nueva opción `timeout` (y `maxContentLength`) en ODataBatch, sin default para no cambiar comportamiento. No rompe nada."
  - New optional `ODataBatch` options `timeout` and `maxContentLength` (numbers). When given they travel in `BatchRequestConfig` (new optional fields) to the repository; the default axios repository forwards them to axios. When omitted, the config carries no such keys (wire and config identical to today).
  - Invalid values (not a finite number >= 0) throw at construction: `<option> must be a non-negative finite number`.
- **S2 DataServiceVersion opt-in.** User choice: "DataServiceVersion opcional" — "Opción para enviar `DataServiceVersion`/`MaxDataServiceVersion: 2.0`. Desactivada por defecto. No rompe nada."
  - New optional option `protocolVersion?: '2.0' | '4.0' | '4.01'`. `'2.0'` adds outer request headers `DataServiceVersion: 2.0` and `MaxDataServiceVersion: 2.0`. Omitted: no version headers (legacy wire unchanged). A caller header with the same name (any casing) wins. Any other value throws `protocolVersion must be '2.0', '4.0' or '4.01'`.
  - Assumption: version headers go on the outer `$batch` request only, not on each inner part.
- **S3 Reject GET inside changesets.** User choice: "Rechazar GET en changesets" — "Cumple la spec v2, pero es BREAKING: hoy se usa en más de 20 tests y probablemente en consumidores. Implica sacar 4.0.0."
  - A `Call` with method `GET` (any casing) in `calls` (flat or grouped) or inside an `operations` changeset throws before sending: `GET is not allowed inside a changeset; use retrieve or operations`. `retrieve` and `operations` GET entries are unaffected.
- **S4 Binary / media parts.** User choice: "Partes binarias/media" — "Permitir Buffer como `data` (subida de ficheros). Feature nueva, esfuerzo medio."
  - `Call.data` may be a `Buffer` or `Uint8Array`. Its bytes are written verbatim; the part keeps the call's own `Content-Type` header (not replaced by the batch-level type). A binary call without its own `Content-Type` throws `Binary call data requires its own Content-Type header`.
  - When any call carries binary data the serialized batch body is a `Buffer` (otherwise still a `string`, byte-identical to today). Boundary-collision rerolls also scan binary payloads.
- **S5 OData v4 multipart.** User choice: "OData v4 multipart" — "Modo v4 reutilizando el wire actual: cabecera OData-Version 4.0 y Content-ID obligatorio en changesets. Esfuerzo bajo-medio."
  - `protocolVersion: '4.0'` adds outer headers `OData-Version: 4.0` and `OData-MaxVersion: 4.0` (caller header wins).
  - `protocolVersion: '4.01'` uses the same multipart behavior with version headers `4.01`.
  - Every changeset member gets a `Content-ID`: explicit ones are kept and must be unique across the whole batch (`Duplicate contentId within the batch: <id>`); missing ones are auto-assigned sequential numbers that never collide with explicit IDs.
- **S6 OData v4 JSON batch.** User choice: "OData v4 JSON batch" — "Formato JSON (`requests[]`, `atomicityGroup`, `dependsOn`): serializador y parser nuevos. Esfuerzo medio-alto, varias sesiones."
  - New option `batchFormat?: 'multipart' | 'json'` (default `'multipart'`). `'json'` requires `protocolVersion: '4.01'` and JSON media types, else throws `batchFormat 'json' requires protocolVersion '4.01' and JSON media types`. Unsupported formats throw `batchFormat must be 'multipart' or 'json'`.
  - Request: POST with `Content-Type: application/json`, body `{ "requests": [...] }`. Each retrieve → `{ id, method: 'get', url, headers }`; each changeset member → `{ id, atomicityGroup, method, url, headers, body }`; `id` = `contentId` or auto-assigned unique; `dependsOn?: string[]` references earlier standalone ids, earlier members of its own group, or completed earlier atomicity groups. Cross-group dependencies must name the group, not an individual member; own-group and forward references are rejected. Binary data → base64url string body with its own `content-type` header.
  - Response `{ "responses": [...] }` (string or already-parsed object) maps to `BatchResponseParsed` (`code` = status as string, `status` = '', `headers` as key/value list, `data` = body or null, `contentId` = id, `changesetIndex` = operation index). Responses correlate by unique id, not service order; unknown/duplicate/unexplained missing ids throw. Failed atomicity groups mark all returned members unsuccessful even for original 2xx responses, preserve the actual failure in grouped output, and allow omitted rolled-back siblings without fabricating responses. Fully omitted later operations after `Prefer: continue-on-error=false` are not reconstructed and remain a documented limitation.
  - `sendGrouped` uses request layout for membership, including singleton changesets whose responses omit `atomicityGroup`. Custom grouped repositories receive an optional sixth parser argument.
  - Confirmed against OASIS JSON Format 4.01 sections 19.1, 19.4, 19.5: JSON batching is a 4.01 feature; no implicit `dependsOn` is added between entries. This corrects the previous agent-authored 4.0 assumption, not a user requirement.
  - Multipart cannot express `dependsOn`: a multipart call carrying it throws `dependsOn requires batchFormat 'json'` (never silently dropped). Done in prep (see L5).
- **S7 Docs.** README and CHANGELOG describe every new option, error message and the BREAKING change of S3.
